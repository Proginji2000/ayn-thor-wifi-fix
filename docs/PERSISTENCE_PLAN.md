# Permanent Wi-Fi patch — persistence qualification

## Product goal
Install once; corrected Wi-Fi code active automatically on every full boot; no PC, manual recovery script or daily user action after installation. Preserve stock PCI runtime PM (auto). Provide a reversible installation, uninstall, firmware compatibility gates and a reproducible patch from the user's own supported firmware artifacts; do not redistribute proprietary binaries. Native vendor integration is the preferred ultimate solution.

## Stage A — parallel stability and boot inventory
Last measured state is stock after V3.6 autonomous watchdog rollback. Preserve acquired evidence; no repeated scan cycles without a changed input or evidence gap. Read-only inventory of stock system/vendor init services, native AYN Settings and privileged service APKs, manifest receivers and supported startup facilities. No native automatic boot mechanism is assumed. Prefer a documented/supported native startup hook if one exists. Determine execution order relative to zygote/system_server and Wi-Fi service; do not automatically restart the framework on each boot without explicit qualification.

## Stage B — design and offline verification
If a supported early-boot hook exists, evaluate verified bind-mount activation before ART loads the Wi-Fi code. If only BOOT_COMPLETED is available, determine whether a safe delayed activation is feasible; app receivers alone do not grant privileged mounts, and late activation may require disruptive framework restart. Treat a privileged helper as fixed-function, narrowly scoped; no arbitrary command interface, no remote commands. Harden local executable and candidate storage (root-owned, not writable by shell/other apps), verify exact build and all stock/candidate hashes, atomic staging, duplicate protection, one attempt per boot, failure marker and opt-out accessible without relying on the corrected Android UI. No automatic reboot loop. Volatile watchdog expiry fault path passed in V3.6; independent boot recovery remains required before enabling any auto-start.

## Stage C — installation and recovery gates
Qualify stock firmware recovery for exact build or equivalent verified recovery method, including backup and restoration plan. First qualify installer/uninstaller and manual boot activation, then supervised cold/warm boots. No partition writes, AVB changes, boot image changes or automatic persistence before recovery and safety gates are met. If no viable supported hook, evaluate vendor integration or a separately reviewed recovery-qualified firmware approach rather than claim persistent installation. Do not publish a stable release before validation.

## Acceptance
- Install once; candidate hashes and executable ART mapping verified on repeated cold and warm boots without user interaction.
- No framework restart loop, no unexpected reboot, no boot lockout, stock PM auto.
- Real Internet connectivity, fresh scans, network changes, sleep/wake and extended normal use.
- Unsupported firmware and OTA mismatch fail closed; no partial activation.
- Opt-out/uninstall and recovery independently verified; next boot returns to original artifacts with no reapplication.
- Document limitations, exact supported builds, install/uninstall and recovery. Publish source and patch/build tooling only; no private logs or proprietary binaries.

## Mandatory lifecycle requirements (user clarification, 2026-11-26)
The deliverable is a maintained open-source permanent patch, not a one-device recovery recipe. Keep source-level transformation and pinned tooling reproducible from legally obtained local stock artifacts; never reuse .377 JAR/ODEX/VDEX on another build by default. Maintain a machine-readable compatibility matrix with exact build, input/output hashes, toolchain versions, qualification status, and recovery prerequisites. Unknown firmware or OTA changes must fail closed with no activation; evaluate each release for the original defect and existing official fix before generating a new candidate. If fixed upstream, retire the patch for that build after validation. Reproducible offline tests, ART compilation and device tests are distinct gates. Publish signed/checksummed releases, changelog, simple bilingual install/uninstall/recovery guide, and an AGENTS.md plus machine-readable preflight/status contract for assisted installation. Separate analysis/build from deployment and require explicit user authorization for boot changes; no blind automated flashing. Keep GitHub CI focused on offline validation and release artifacts, not unqualified physical device tests. Report the defect and proposed correction privately to AYN first, coordinate disclosure with maintainers; public community documentation must omit private network data, proprietary binaries and trigger construction. Do not assume future OTA releases remain defective. Magisk is a candidate delivery mechanism, not a mandatory dependency until qualified; prefer vendor fix or supported native delivery where possible. No automatic firmware deployment from update monitoring.
